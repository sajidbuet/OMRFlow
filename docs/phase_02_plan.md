# Phase 2 plan — Template Data Model & Template Designer Core

**Written before implementation**, per the Phase 2 brief. This records the
interpretation of the existing repository and the decisions made to fit the
designer onto it rather than build a second, competing structure.

## 1. Existing architecture (as found)

- **Layering is executable.** `tests/unit/test_architecture.py` parses every
  source file's imports and fails the build if `gui` imports `cv2`, `numpy`,
  `sqlalchemy`, `omr_scanner.database`, `omr_scanner.imaging` or
  `omr_scanner.recognition`; if `imaging` imports Qt; if `domain` imports
  anything above it. This is the hardest constraint Phase 2 must respect and it
  shapes almost every design decision below.
- **The `.omrt` template format already exists** (`omr_scanner.domain.template`,
  Phase 0) and already matches most of what the Phase 2 brief asks for:
  - `RegistrationMarker` (four, one per corner role) and `OrientationMarker`
    already store explicit geometry.
  - `Zone` + `FieldDefinition` (`numeric`, `alphanumeric`, `set_code`,
    `question_block`, `ignored`) + `BubbleGrid` (pitch + explicit
    `BubbleOverride`s) already give every bubble a logical identity computed
    from a stored pitch, not "one rectangle per region" — exactly what §13 of
    the brief asks for, and it is **already tested** (`test_template_model.py`).
  - Coordinates are normalised `[0, 1]` against the canonical page
    (`omr_scanner.domain.geometry`), matching §20 of the brief.
  - `services.template_service` already loads/saves/validates `.omrt` files.
- **Phase 1 delivered a complete alignment/detection engine**
  (`omr_scanner.imaging`) with marker candidate measurement and per-corner
  selection (`marker_detection.py`) that already does the "search independently
  in four zones, filter by darkness/area/squareness/geometry/location" the
  brief asks for in §7 — it must be *reused*, not reimplemented.
- **Errors** carry a technical message and a `user_message`; `TemplateError`
  and `ImagingError` already exist.
- **GUI pages** are `WorkflowPage` subclasses registered in
  `gui/pages/catalog.py`; the "Template" stage is currently a
  `PlaceholderPage` naming Phase 2.

## 2. Decision: no second template format

The brief's suggested JSON shape (§19) and marker model (§8, with
`detection_method`/`confidence`/`confirmed`) are **not** adopted verbatim.
Instead:

- **The persisted document stays `OmrTemplate`** (`format = "omrflow-template"`,
  `format_version = 1`). Inventing a parallel `schema_version: "1.0"` shape
  would give the project two competing template formats for no benefit, which
  §39 explicitly warns against.
- **One additive field is added** to `OmrTemplate`:
  `reference_image: str | None = None`, a path to the source image relative to
  the template file's directory (matching the relative-path convention in
  ADR‑0002). This is what lets "reload an existing template and continue
  editing" (§1.10) work without embedding image bytes (§19 explicitly forbids
  base64 images). Per `docs/TEMPLATE_FORMAT.md`, additive optional fields do
  not bump `format_version`; a document without the field still loads, with
  `reference_image = None`.
- **Detection provenance (`detection_method`, `confidence`, `confirmed`) is
  kept as GUI-session state, not persisted.** It is scaffolding for the
  *editing session* — once a marker is saved, a scanner only needs its
  geometry, and the domain model already stores that. Persisting a
  `confidence: float` for a marker a user placed by hand five edits ago would
  be meaningless. This is documented in `docs/template_designer.md` as a
  deliberate simplification.

## 3. Decision: regions are `Zone`s, generated by pure domain functions

The brief's five region kinds map onto the existing `FieldType` enum with no
new domain types:

| Brief region | `FieldType` | Notes |
|---|---|---|
| Student ID | `numeric` | Existing `GridFieldDefinition`. |
| Question Set | `set_code` | Existing `GridFieldDefinition`. |
| Question Answer block | `question_block` | A "4 columns × 25 questions" layout is generated as **four `Zone`s**, one per column — `docs/TEMPLATE_FORMAT.md` already documents this as the intended shape ("Long papers are described as several blocks, one per printed column"), so nothing new is needed here either. |
| Custom bubble group | `alphanumeric` | User supplies the symbol set; same grid machinery. |
| Reference/logo region | `ignored` | Existing. |

A new pure module, `omr_scanner/domain/template_authoring.py`, adds the
generator functions (`generate_student_id_zone`, `generate_question_set_zone`,
`generate_question_columns`, `generate_custom_bubble_zone`) plus a
designer-level validation pass (`validate_template_for_designer`) that reports
**errors** and **warnings** beyond what Pydantic already enforces (region
overlapping a registration marker, no zones defined at all, etc.). This module
is pure Python/Pydantic — no Qt, no OpenCV, no I/O — so it is unit-testable
exactly like the rest of `domain` and never needs a display.

## 4. Decision: an immutable document plus a snapshot-stack for undo/redo

`OmrTemplate` is a frozen Pydantic model. Rather than building a second mutable
mirror of it (a classic source of drift), **the designer edits by producing a
new `OmrTemplate` via `model_copy(update=...)` and pushes the result onto a
history stack** (`gui/template_designer/history.py`, pure Python, no Qt). This
means:

- Undo/redo is a plain list of `OmrTemplate` snapshots with an index — no
  command classes to keep in sync with the model.
- **Coalescing** happens naturally: a drag or resize gesture only pushes one
  snapshot, at mouse-release, not per mouse-move event (§24's explicit
  requirement).
- Save is `save_template(history.current, path)` — the exact object being
  edited, so round-trip equality is automatic, never approximated.
- The whole thing is testable without instantiating a single `QWidget`.

## 5. Decision: the GUI never touches `cv2`/`numpy` directly

Marker detection and image decoding are Phase 1 (`omr_scanner.imaging`) and
must not be imported from `gui`. A new service,
`omr_scanner/services/marker_detection_service.py`, is the seam:

- `decode_image_file(path) -> DecodedImage` — a **plain dataclass**
  (`width: int, height: int, channels: int, data: bytes`) built by decoding the
  file with `services.alignment_service.load_scan_image` and calling
  `.tobytes()` on the array *inside the service*. The GUI builds a `QImage`
  directly from those bytes (`QImage(bytes, width, height, stride, format)`) —
  no `numpy`/`cv2` import needed in `gui` at all, verified by the existing
  architecture test.
- `detect_registration_markers(path, config) -> MarkerDetectionOutcome` reuses
  `imaging.preprocessing.prepare_for_detection`,
  `imaging.marker_detection.detect_marker_candidates` and
  `select_corner_markers` — the exact Phase 1 detector, run on the *raw*
  reference image (not through `align_sheet`, which assumes a template's
  marker geometry already exists — the inverse of what the designer needs).
  Detection failures per corner (`InsufficientMarkersError` naming the corner,
  `AmbiguousMarkerError`) are caught and turned into a per-corner "not found"
  result rather than aborting the whole detection pass, so three good corners
  plus one to place by hand is the normal, expected outcome — never a crash.
- Both functions return only dataclasses of `int`/`float`/`bytes`/`str`; the
  service module is the only place in Phase 2 that imports `cv2`/`numpy`.

## 7. Data flow

```text
File > New Template from Image
    │
    ▼
services.alignment_service.load_scan_image()  (decode)
services.marker_detection_service.decode_image_file()  (bytes for display)
    │
    ▼
TemplateDesignerPage builds a QImage/QPixmap, shows it in TemplateCanvasView
    │
    ▼
User clicks "Detect Markers"
    │
    ▼
services.marker_detection_service.detect_registration_markers(path, config)
    │  (imaging.preprocessing + imaging.marker_detection under the hood)
    ▼
Per-corner DetectedMarkerResult (found: x,y,w,h,score | not found: reason)
    │
    ▼
TemplateDesignerState seeds RegistrationMarker geometry (normalised) +
per-marker session status (auto/manual/confirmed) — drawn on the canvas
    │
    ▼
User places/drags markers, orientation mark, adds regions via dialogs
(Student ID / Question Set / Question Block / Custom) → domain generator
functions in template_authoring.py build Zone objects
    │
    ▼
Each completed edit → OmrTemplate.model_copy(update=...) → TemplateHistory.push()
    │
    ▼
File > Save → validate_template_for_designer() → services.save_template()
```

## 8. Key design decisions (summary)

1. Reuse `OmrTemplate` as the single source of truth; no parallel schema.
2. Undo/redo is a snapshot stack over the immutable document, coalesced at
   gesture boundaries — not a command-object hierarchy.
3. Marker/orientation *detection provenance* is session state, not persisted;
   geometry is persisted, exactly as the existing domain model already
   requires.
4. All pixel/array work stays behind `services.marker_detection_service`; the
   GUI only ever holds `bytes`, `int`, `float`, `QImage`/`QPixmap`.
5. Question blocks are generated as one `Zone` per column, matching the format
   this document already specified before Phase 2 began.
6. Individual-bubble editing reuses the existing `BubbleOverride` mechanism —
   no new geometry concept, just a UI to create/clear overrides.
